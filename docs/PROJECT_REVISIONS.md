# Project save revisions

Apply `docs/schema/VFOPT_X_001_F001.sql` once to the existing database before starting this API version. This additive patch has been applied to the configured MySQL database used by the local API. The configured database is remotely hosted. It preserves project content and gives existing projects revision `0`. Flyway remains disabled: this checkout does not contain the database's original migrations 1–4. Other environments need the same schema patch before deploying the API and UI together.

Project create, read, fork and save responses include `documentRevision`, a decimal string independent of `updatedAt`. Send the most recently acknowledged token as `expectedRevision` in every project PUT. Missing tokens return 400; stale or old timestamp tokens return 409 `PROJECT_REVISION_STALE`. Old editor tabs must reload after the upgrade.

The save transaction checks ownership and the supplied token, then Hibernate checks `document_revision` again in the actual UPDATE through `@Version`. There is no early `SELECT FOR UPDATE` lock while the document is being uploaded to MySQL. The parent is marked changed even for code-only/no-op saves, so its version is advanced at flush before the acknowledgement is mapped. A competing write rolls back the whole transaction, including child code files, and returns 409. Dynamic updates also avoid retransmitting unchanged JSON fields or overwriting concurrently incremented counters.

View and fork counter queries explicitly preserve `updated_at`, suppressing the legacy MySQL automatic timestamp update. Counters never change `document_revision`. Timestamps remain display/list metadata, not save tokens.

WebSocket canvas events remain authorized live broadcasts, but no longer schedule a second unacknowledged database write. The owner editor persists the complete document through the guarded REST path: Save, two-second idle autosave, or the ten-second continuous-edit/retry interval. This keeps canvas, code and PCB state under one acknowledgement contract. Subscribers see live previews; successful REST saves establish durable state. Shared-editor persistence beyond the existing owner-only UI is not introduced here.

Project POST/PUT JSON bodies have a **4 MiB UTF-8 byte limit**, including JSON escaping, field names and revision metadata. The server reads at most that limit plus one byte before parsing or opening the save transaction; both Content-Length and chunked uploads are covered. Oversized requests receive 413 `PROJECT_PAYLOAD_TOO_LARGE`. The editor checks the same budget before uploading. Code-file validation applies recursively: at most 50 files, each up to 1,000,000 characters, with valid filenames. These REST limits are independent of Live Sync's 1 MiB frame budget.

On rejection, the current tab retains its authored document and dirty flag. Automatic retries pause for an unchanged document after size, validation or revision errors. A real edit or explicit Save can retry. This is in-memory recovery, not a durable offline draft: keep a copy before closing/reloading an unsaved tab.

MySQL connections use protocol compression inside the existing TLS connection. The driver bounds connection establishment to 5 seconds and socket reads to 15 seconds. Create/update/delete transactions have a 20-second timeout; row lock waits are limited to 5 seconds. If a connection reset prevents rollback from reaching the server, a 60-second **session** idle timeout bounds an abandoned transaction; the existing 30-second Hikari keepalive maintains healthy idle connections. No server-wide settings are changed. Normal failed writes roll back immediately; the idle bound is the fallback for a broken network path. Database availability/timeout failures return 503 `DATABASE_UNAVAILABLE`; an unconfirmed commit must never be treated as a successful save or automatically replayed without the revision guard.

The driver and session settings are in the non-test configuration document in `application.yml`; H2 tests use the `test` profile. They follow the [Connector/J networking properties](https://dev.mysql.com/doc/connector-j/en/connector-j-connp-props-networking.html) and MySQL [session timeout definitions](https://dev.mysql.com/doc/refman/8.4/en/server-system-variables.html#sysvar_wait_timeout). The original peer reset was intermittent; application changes do not establish which upstream network component sent it.
